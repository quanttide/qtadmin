# 评审页设计

评审页承载「接受评审结果」：执行完成后必须有明确评审人接收结果，职责不再默认回流创始人。

## 定位

对齐洞察 review-path 第三步「评审动作」与第四步「闭环跟踪」：对照执行契约检查，结论必留痕，打回原因成为制度修订的输入。

## 数据

评审结果承载在 Task 上（MVP 不建独立评审实体）：

| 字段 | 说明 |
|------|------|
| reviewer | 评审人 |
| reviewNote | 评审意见（通过备注 / 打回原因） |
| reviewedAt | 评审日期 |

## 交互

页面分两个区块：

- 待评审：inReview 状态的任务卡片，展示执行人、截止日期、交付物，操作「通过」与「打回」
- 已评审：approved / rejected 状态的任务列表，展示评审人、日期、意见

评审动作弹窗要求填写意见：通过填备注，打回填原因（原因即制度修订的输入）。

## 状态流转

- 通过：inReview → approved
- 打回：inReview → rejected，执行人修改后重开再提交
